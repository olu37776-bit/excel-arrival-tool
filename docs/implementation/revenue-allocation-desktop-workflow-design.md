## 1. 文档目的

本文件冻结收入分配新工作簿在桌面端的用户任务、入口、文件选择、跨期比较和分配刷新语义。

本次只定义产品流程，不修改生产代码。后续实现必须保持已经批准的收入分配领域模型和计算规则，不得在 GUI 或 Excel Writer 中重新实现业务计算。

## 2. 当前问题

当前 GUI 将以下输入合并为一个字段：

```text
上一次结果 / 已分配结果（可选）
```

但该文件在当前 `run_pipeline` 中同时承担两项不同职责：

1. 继承用户填写的手工分配金额和分配备注；
2. 作为 RPD/CPD 履行投影跨期比较的上期基线。

这使两个不同的用户任务被迫使用同一个运行入口。

### 2.1 问题场景

```text
上期源数据 S0
→ 上期结果 R0

本期源数据 S1 + R0
→ 本期结果 R1
→ R1 正确记录 S0 → S1 的 RPD/CPD 跨月变化

用户在 R1 中填写手工金额和备注

同一份本期源数据 S1 + R1
→ 刷新结果 R2
```

当前实现会把 R1 同时当作金额继承来源和跨期比较基线，因此第二次比较实际变成：

```text
S1 当前履行投影
对比
R1 中保存的 S1 履行投影
```

两边履行投影相同，R2 的 RPD/CPD 跨月变化会变为空，原本正确的 `S0 → S1` 变化证据被清除。

该问题通常不会制造虚假的跨月变化，但会丢失本期已经生成的正确跨期变化。它是当前产品闭环缺口，不得作为正常行为保留。

## 3. 产品设计原则

### 3.1 以用户任务为入口

用户不需要理解以下内部概念：

- `run_pipeline`；
- `PreviousRunState`；
- allocation inheritance；
- projection comparison baseline；
- metadata schema。

界面只呈现两个业务任务：

1. 生成新一期结果；
2. 更新已填写的分配。

### 3.2 渐进展示

首页不得同时展示所有源文件、历史结果和输出路径控件。用户选择任务后，只展示该任务需要的输入。

### 3.3 一个入口只改变一类状态

- “生成新一期结果”允许改变源数据事实、履行投影和跨期变化；
- “更新已填写的分配”只允许改变分配金额、备注、分配状态、待处理和月度结果。

### 3.4 自动识别，明确反馈

源文件角色由字段契约识别，不要求用户理解内部 Sheet 名或文件角色配置。自动识别结果必须在执行前向用户展示。

### 3.5 默认安全另存

任何操作都不得覆盖：

- 源文件；
- 上期结果；
- 用户已经填写的本期结果。

## 4. 首页信息架构

首页只显示两个任务入口，不使用“运行模式”下拉框、单选按钮或包含全部字段的统一表单。

```text
收入预测工具

┌──────────────────────────────┐
│ 生成新一期结果               │
│ 读取新的源数据，继承上期分配 │
│ 并生成新的跨月变化           │
└──────────────────────────────┘

┌──────────────────────────────┐
│ 更新已填写的分配             │
│ 读取已经填写金额的本期结果， │
│ 重新生成分配状态和月度汇总   │
└──────────────────────────────┘
```

首页可以显示最近一次成功生成的结果路径，但不得自动执行任何操作。

## 5. 任务一：生成新一期结果

### 5.1 适用场景

以下任一情况发生时使用：

- 遗留量源数据发生变化；
- 当月订货源数据发生变化或本期首次提供；
- 要货明细发生变化；
- 国家运输周期发生变化；
- 进入新的统计期；
- 需要根据最新源数据重新生成履行投影和跨月变化。

### 5.2 界面

```text
生成新一期结果

本期源数据
[ 选择 Excel 文件 ]
支持一次选择多个文件

识别结果
✓ 遗留量：legacy.xlsx
✓ 要货明细：demand.xlsx
✓ 国家运输周期：transit.xlsx
○ 当月订货：未提供（允许）

上期最终结果（可选）
[ 选择上期结果 ]

保存位置
默认：源文件目录/收入预测结果-YYYY-MM-DD-HHmm.xlsx
[ 更改保存位置 ]

[ 生成新一期结果 ]
```

### 5.3 输入规则

源数据使用一个多文件选择入口。系统读取文件和 Sheet 的字段指纹后识别：

- `legacy`；
- `monthly_order`；
- `demand_detail`；
- `transit`。

规则：

- `legacy`、`demand_detail`、`transit` 必须各有且只有一个；
- `monthly_order` 可以没有，但不能存在多个候选；
- 新版结果工作簿不能被识别为源文件；
- 多个文件同时符合相同角色时停止执行并要求用户处理歧义；
- 缺少必选角色时明确显示缺少的角色；
- 不要求用户选择或输入业务 Sheet 名。

### 5.4 上期结果作用

上期最终结果仅用于：

- 恢复上期 FulfillmentProjection；
- 进行 RPD/CPD 跨期比较；
- 按 candidate ID 继承上期手工金额和备注；
- 识别候选新增、消失和 orphaned 历史金额；
- 比较 projection fingerprint 和合同收入预测。

如果未提供上期结果：

- 正常生成本期合同、候选、分配和汇总；
- RPD/CPD 跨月变化为空；
- 不伪造历史金额或变化诊断。

### 5.5 执行语义

```text
新一期源数据
→ ContractFinancialFact
→ DemandRecord
→ FulfillmentProjection
→ 与上期 FulfillmentProjection 比较
→ RevenueAllocationCandidate
→ 历史金额继承与候选诊断
→ 分配、待处理、Posting 和两套月度汇总
→ 新一期结果工作簿
```

本任务会重新生成：

- 合同收入预测；
- 收入分配；
- RPD/CPD 月度收入汇总；
- 待处理收入；
- 收入归月明细；
- 要货记录明细；
- RPD/CPD 跨月变化；
- 供应需要提拉诉求清单粗表；
- 异常清单；
- 两个隐藏系统数据集。

## 6. 任务二：更新已填写的分配

### 6.1 适用场景

本期源数据和履行事实没有变化，用户只在本期结果的“收入分配”Sheet 中填写或修改了：

- 手工分配金额；
- 分配备注。

### 6.2 界面

```text
更新已填写的分配

已填写的本期结果
[ 选择结果文件 ]

检测结果
合同数：125
分配候选数：148
已填写手工金额：37
仍未分配合同：12
本期源数据快照：完整
跨期比较结果：将保持不变

保存位置
默认：原文件目录/收入预测结果-分配更新-YYYY-MM-DD-HHmm.xlsx
[ 更改保存位置 ]

[ 更新分配和月度汇总 ]
```

### 6.3 输入规则

本任务只允许选择 metadata schema `4` 或后续兼容版本的新结果工作簿。

不要求重新选择：

- 遗留量；
- 当月订货；
- 要货明细；
- 国家运输周期；
- 上期结果。

v0.8 结果不能作为本任务的当前结果输入，因为它不包含新分配候选、手工金额和完整往返数据。界面必须提示用户使用“生成新一期结果”。

### 6.4 允许变化的数据

只重新读取和计算：

- 手工分配金额；
- 分配备注；
- 最终分配金额；
- 分配来源；
- 合同已分配/待分配金额；
- 分配状态；
- 分配金额相关异常；
- 待处理收入；
- RPD/CPD Posting；
- RPD/CPD 月度汇总；
- 合同预测表中的金额状态摘要；
- GUI 完成摘要。

### 6.5 必须保持不变的数据

本任务不得重新计算或改变：

- ContractFinancialFact 的源数据事实；
- DemandRecord；
- FulfillmentProjection；
- candidate ID；
- projection fingerprint；
- RPD跨月变化；
- CPD跨月变化；
- 供应需要提拉诉求清单粗表；
- 所有源文件指纹；
- 本期源数据对应的业务运行标识；
- 与源数据相关的异常证据。

### 6.6 执行语义

```text
已填写的本期结果工作簿
→ 恢复本期 ContractFinancialFact
→ 恢复本期 FulfillmentProjection
→ 恢复本期 RevenueAllocationCandidate
→ 读取手工分配金额和备注
→ 重新计算分配、待处理和 Posting
→ 重新生成 RPD/CPD 月度汇总
→ 保留本期原始跨期变化和源数据证据
→ 新的分配修订工作簿
```

该任务不是一次新的业务期运行，不得把当前工作簿当作自己的“上期履行比较基线”。

## 7. 结果工作簿的修订身份

为区分“源数据运行”和“分配修订”，metadata 后续实现至少需要表达：

```text
business_run_id
allocation_revision_id
allocation_revision_number
allocation_revised_at
source_file_fingerprints
comparison_baseline_business_run_id
```

定义：

- `business_run_id`：同一批源数据产生的业务结果身份；分配刷新时保持不变；
- `allocation_revision_id`：每次分配刷新产生的新修订身份；
- `allocation_revision_number`：同一业务运行内从 0 开始递增；
- `comparison_baseline_business_run_id`：本期跨月变化所使用的上期业务运行身份；
- `run_id` 可以继续保留用于兼容，但不得单独承担上述两个语义。

分配刷新后，下期“生成新一期结果”可以选择最新分配修订作为上期结果：

- 履行比较仍使用该工作簿保存的本期 FulfillmentProjection；
- 金额继承使用最新修订的手工金额和备注；
- 不影响下期跨月比较正确性。

## 8. 工作簿内编辑规则

“收入分配”Sheet 中仅以下两列可编辑并保持黄色底色：

```text
手工分配金额
分配备注
```

用户在 Excel 内保存后，月度汇总不会在同一工作簿中即时刷新。界面和 Sheet 表头说明必须明确：

```text
填写完成后，请保存工作簿并在工具中选择“更新已填写的分配”，
工具将生成一份新的分配及月度汇总结果。
```

不在 Excel Writer 中加入重新实现业务规则的复杂公式或宏。

## 9. 输出命名

默认输出名称必须包含业务含义和时间，避免覆盖：

```text
生成新一期：收入预测结果-YYYY-MM-DD-HHmm.xlsx
更新分配：收入预测结果-分配更新-YYYY-MM-DD-HHmm.xlsx
```

EXE Artifact 和 Release 文件名必须包含版本号：

```text
分支测试版：ExcelRevenueTool-v<version>-RevenueE2E.exe
正式版本：ExcelRevenueTool-v<version>.exe
```

## 10. 错误和提示设计

错误信息面向用户任务，不直接暴露堆栈或内部类名。

示例：

```text
未识别到“要货明细”文件。请确认已选择包含合同号、供应中心和日期字段的Excel文件。

发现两个文件都可能是“遗留量”。请只保留一个后重新选择。

所选文件是v0.8旧结果，不能直接更新分配金额。请使用“生成新一期结果”。

所选本期结果缺少系统数据，无法安全刷新汇总。原文件未被修改。
```

执行前显示系统识别结果；执行后显示：

- 输出文件；
- 合同数；
- 分配候选数；
- 已分配金额；
- 待分配金额；
- RPD归月金额；
- CPD归月金额；
- 待处理记录数；
- 异常数。

## 11. 非目标

本产品流程调整不改变：

- candidate ID v1；
- projection fingerprint v1；
- 合同收入预测公式；
- FulfillmentProjection 粒度和履行计算；
- 自动分配条件；
- 部分分配和超额规则；
- RPD/CPD Posting 和汇总口径；
- v0.8 兼容规则；
- 新工作簿的可见 Sheet 契约；
- 仅两列可编辑的规则。

不建设复杂前端、账号系统、数据库或在线服务。

## 12. 实施边界建议

后续代码实现应分别建立两个应用层用例，避免 GUI 自己判断业务：

```text
GeneratePeriodResultUseCase
RefreshAllocationResultUseCase
```

建议职责：

- GUI：选择任务、收集文件、展示识别结果和完成摘要；
- 文件识别服务：识别源文件角色和结果工作簿版本；
- 新一期用例：读取源数据、构建领域模型、跨期比较、继承和完整输出；
- 分配刷新用例：恢复本期领域状态、读取人工输入、重新分配和汇总；
- Writer：展示数据，不计算业务规则；
- metadata：区分业务运行与分配修订。

不得通过在现有 `run_pipeline` 增加大量布尔参数实现两个任务，也不得在 GUI 中复制 pipeline 业务编排。

## 13. 验收标准

### 13.1 首页

- 首页只显示两个业务任务入口；
- 不同时显示全部文件输入框；
- 用户无需理解“运行模式”或内部状态名称。

### 13.2 生成新一期

- 一个文件选择入口支持多选源文件；
- 自动识别三个必选角色和一个可选角色；
- 可以选择上期最终结果；
- 新源数据正确生成新的 RPD/CPD 跨月变化；
- 最新手工金额和备注按冻结规则继承。

### 13.3 更新分配

- 只选择一个已填写的新格式结果即可执行；
- 不要求任何源文件；
- 空白、明确 0、正数和负数金额均正确读取；
- 分配、待处理、Posting 和两张汇总正确更新；
- 原 RPD/CPD 跨月变化逐字段保持一致；
- 原履行投影、candidate ID和fingerprint保持一致；
- 输入结果工作簿不被覆盖。

### 13.4 连续运行

必须通过以下自动化场景：

```text
S0 → R0
S1 + R0 → R1（生成跨月变化）
R1 填写手工金额 → R1a（刷新分配）
验证 R1a 保留 R1 的跨月变化
验证 R1a 更新两张月度汇总
S2 + R1a → R2
验证 R2 比较 S2 与 S1，而不是错误比较分配修订
验证 R2 继承 R1a 的最新金额和备注
```

还必须覆盖：

- 刷新多次仍保持同一 `business_run_id`；
- 分配修订号连续递增；
- 源数据集指纹保持不变；
- 刷新时缺少必要隐藏数据则安全失败；
- v0.8旧结果不能进入分配刷新；
- Windows EXE两个入口 smoke test；
- Windows桌面Excel编辑、保存、刷新实机验证。

## 14. 当前结论

产品流程设计结论：`READY_FOR_BUSINESS_CONFIRMATION`。

当前生产 EXE 尚未实现本文件定义的双任务入口。现有 E2E 路径可以重新读取人工金额并生成汇总，但会在同源数据刷新时重新建立跨期比较基线，从而清除本期原有跨月变化。

在本文件获得确认并完成代码、往返测试和 Windows EXE 验证之前，不应把“更新已填写的分配”描述为已经完成的独立用户任务。
