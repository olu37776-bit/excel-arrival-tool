## 2. RPD 命名修正

业务方最新提供的正式目标字段为 `RPD`，并且最终输出字段明确为：

- `RPD`
- `到货日期（按RPD）`
- `收入年月（按RPD）`

因此，从本文件建立起，目标输出侧以 `RPD` 为 canonical name。

此前需求基线和 POC 中出现的 `PRD` 不得继续被默认视为正确字段名。后续需要用实际要货明细表确认源字段是否同样为 `RPD`；若确认，则需求基线中的所有 PRD 规则应统一迁移为 RPD，并记录一次显式变更。

## 3. 人工维护字段与跨次继承

以下字段由用户人工填写，不由本次源表重新计算：

1. `收入分段类别`
2. `是否手工调整收入月份`
3. `手工调整收入月份`
4. `调整备注`

当前确认规则：

- 新一轮运行生成基表时，若能在上一轮结果中找到对应业务记录，则继承上一轮这四个字段的值；
- 本次计算不得覆盖已继承的人工值；
- 首次出现、且上一轮没有对应记录时，这四个字段默认为空，等待人工填写；
- 继承所使用的稳定匹配键尚需最终确认，当前候选为 `合同号 + 供应中心`。

## 4. 已确认的相关业务基础

### 4.1 输出粒度

最终一条正常业务记录当前按：

`合同号 + 供应中心`

形成。同一合同号存在多个供应中心时输出多行。

### 4.2 国家

国家当前优先从遗留量表取得；无有效值时再取要货明细表。同一合同号必须唯一国家，否则记数据异常。

### 4.3 海运周期

基础海运周期按：

`国家 + 供应中心`

从国家运输周期表匹配，单位为自然日。部分特殊贸易类型会调整海运周期，具体规则后补但属于业务代码规则。

### 4.4 日期聚合

在同一 `合同号 + 供应中心` 范围内：

- ATA：取最大有效日期；
- ASD：取最大有效日期；
- RPD：当前按此前已确认的“最早计划日期”逻辑理解为取最小有效日期，但需在源字段 RPD 命名确认后正式冻结；
- CPD：取最大有效日期。

### 4.5 到货日期

当前规则理解为：

**按 RPD**
- 有 ATA：取 MAX(ATA)，不加海运周期；
- 无 ATA、有 ASD：取 MAX(ASD)，不加海运周期；
- ATA/ASD 均无：MIN(RPD) + 最终海运周期。

**按 CPD**
- 有 ATA：取 MAX(ATA)，不加海运周期；
- 无 ATA、有 ASD：取 MAX(ASD)，不加海运周期；
- ATA/ASD 均无：MAX(CPD) + 最终海运周期。

收入年月分别取对应到货日期的年月。

## 5. 后续字段规则需要补充的统一模板

每个非人工字段后续至少补齐：

- 来源表；
- 源业务字段准确名称；
- 匹配键；
- 多条记录时的聚合规则；
- 空值时是否回退到第二来源；
- 冲突时是否报错；
- 是否参与后续计算；
- 是否需要跨次继承/对比。

对于派生标记字段，还需补充：

- 触发条件；
- 输出值（例如 是/否、Y/N、具体类别）；
- 计算粒度（合同级或合同+供应中心级）。

## 6. 当前优先待确认事项

1. 源要货明细中的正式字段是否确实叫 `RPD`，从而彻底替换此前的 `PRD`。
2. `遗留量`、`当月新订货` 在一合同多供应中心时如何展示/统计，避免合同级金额被重复计算。
3. `地区部`、`结转类型`、`客户群`、`项目名称`、`贸易术语` 的来源与回退优先级。
4. `多个供应中心发货`、`多次要货`、`分批供应`、`分批发货` 的准确判定条件。
5. `是否解锁备货` 的来源和业务含义。
6. 四个人工字段跨次继承的稳定匹配键，以及供应中心变化、新增/删除行时的继承策略。
7. `手工调整收入月份` 对最终统计口径的影响：只是展示人工值，还是覆盖按 RPD/CPD 算出的某个收入年月。
